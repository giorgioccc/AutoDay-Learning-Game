# AutoDay

Real AI automation problems. No answers handed over.

AutoDay hands you a concrete automation problem — a specific person doing
repetitive work by hand — and makes you work out how you would build it before
it shows you anything. Help is revealed one layer at a time and stops at the
architecture. There is no finished solution and no copy-paste code anywhere in
the product.

Fifty challenges, two modes, two languages, no backend.

## Running it

Requires Node 20.9+ (built against 24.19.0 LTS).

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # production build, fully static
npm run lint
npx tsc --noEmit
```

Deploys to Vercel with no configuration. Set `NEXT_PUBLIC_SITE_URL` to the real
domain so `metadataBase`, `robots.txt` and `sitemap.xml` point at it — it falls
back to `https://autoday.vercel.app`.

## Where the content lives

```
src/content/types.ts             The Challenge contract. Treat changes as breaking.
src/content/challenges/*.ts      One file per challenge.
src/content/challenges/index.ts  The registry, matchingChallenges() and pickFrom().
src/lib/i18n.ts                  Every UI string, in both languages.
src/lib/filters.ts               Filter state, validation and localStorage.
src/lib/timer.ts                 The session timer hook and its presets.
```

Components never hardcode copy. Adding challenges touches data files only.

## Adding a challenge

1. Copy an existing file in `src/content/challenges/`. `monday-filter.ts` is
   the quality benchmark — read it first.
2. Fill in **every** field in both `en` and `it`. All fields are required.
   `level` and `category` drive the filters, `estimatedMinutes` drives the
   timer presets, and `id` becomes a permanent URL — renaming one breaks
   every link to it.
3. Import it in `src/content/challenges/index.ts` and add it to the
   `challenges` array. That single array is the registry, the filter source
   and the sitemap.
4. Read `CONTENT.md` before writing a word of it. The writing rules there are
   the product; a vague challenge is worse than no challenge.

`constraints`, `approach.steps` and `pitfalls` are arrays of `{ en, it }`
objects, so both languages must have the same number of bullets.

## Architecture notes

- Statically generated. No backend, no database, no API keys, no LLM calls at
  runtime — the whole library ships as typed data in the bundle.
- The interactive parts are client components, but Next still server-renders
  them at build time, so the idle screen and the explanatory prose are real
  static HTML in the response body.
- The three reveals are `<details>` elements, so their content is in the DOM
  and works without JavaScript. The starter prompt is the deliberate exception:
  while its checkbox is unchecked it is not rendered at all, so nobody solving
  a challenge unaided can catch sight of it by accident.
- Every challenge also has its own static page at `/c/<id>`, generated by
  `generateStaticParams` with `dynamicParams = false`, so an unknown id is a
  real 404 rather than a runtime render. The permalink view deliberately has
  no spinner: someone was sent that specific problem.
- Language is stored on `<html lang>`, set from `localStorage` by a tiny inline
  script before first paint, and read by React through `useSyncExternalStore`.
  That avoids both a flash of English and a hydration mismatch.
- The filters use the same external-store trick for the same reason. Stored
  values are validated against the canonical category and level lists on read,
  so a renamed category cannot resurrect itself out of someone's browser.
- **`localStorage` holds the language preference, the filters and an optional
  theme override, and nothing else.** No accounts, no progress, no
  favourites, no analytics — by design.
- The session timer is opt-in, offered only once there is something to time,
  and derived from a stored end timestamp rather than accumulated by an
  interval — a backgrounded tab or a closed laptop lid cannot make it wrong.
  When it runs out it says so and keeps counting; nothing beeps, blocks or
  hides. Both timestamps live in one piece of state so no clock is read
  during render.
- Dark mode follows `prefers-color-scheme` by default and needs no script to
  do so. `ThemeSwitch` can pin it explicitly to light or dark — that choice
  lives on `<html data-theme>`, applied before first paint the same way the
  language is, and is the one case where the CSS declares the dark tokens
  twice (once behind the media query, once behind the attribute) since a
  stylesheet can't "or" the two together.
- All text meets WCAG AA contrast in both palettes, verified by walking the
  rendered DOM with every disclosure open. `--on-accent` exists because the
  dark palette's accent is a pale lavender and white text on it is unreadable.

## Design system

Terminal aesthetic, light-editor palette. Tokens are CSS custom properties in
`src/app/globals.css`, exposed to Tailwind v4 through `@theme inline`.

Monospace (JetBrains Mono) for the wordmark, headings, metadata, labels and
buttons; Inter for scenarios and other multi-sentence prose. That split is the
whole look — keep it.
